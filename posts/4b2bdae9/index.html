我给自己博客写了一套封面生成规则：630×487 的封面是怎么算出来的

发表于2026-11-22|更新于2026-11-22|博客
|浏览量:

先说结论

我给这个博客的每一篇文章都配了两张自己画的 SVG 图：首页卡片的封面，和文章页顶部的横幅。

它们不是同一张图的两个尺寸，而是两张按各自容器比例独立设计的图：

尺寸 比例 用在哪
封面 cover 630×487 1.294 : 1 首页卡片左侧图框（348×269）
横幅 banner 1600×400 4 : 1 文章页顶部 #page-header.post-bg（400px 高）

这两个数字都不是拍脑袋定的，是从 CSS 反推出来的。下面把推导过程、坐标参数、以及六轮目检踩出来的迭代规则一次讲清。

一、首页卡片到底会不会裁你的图

先看现象。butterfly 的首页文章卡片是 flex 布局，图片区 .post_cover 的宽度是 42%，高度由父容器 16.8em 决定。图片本身是 object-fit: cover。

object-fit: cover 的意思是：等比缩放到刚好填满容器，超出的部分居中裁掉。

所以问题变成：一张 1200×500 的横图放进 348×269 的框里，会发生什么？

答案是左右各裁掉约 149px，一共丢掉 30% 的画面宽度。如果你的标题是烘焙在图片里的，它很可能刚好被裁断。

换成 630×487 就没事了：

两个比值一致，cover 缩放时横向和纵向的缩放因子相同，一个像素都不用裁。这就是 630 和 487 这两个数字的全部来历——不是设计感，是让浏览器无事可做。

二、横幅为什么不能复用封面

一开始我想偷懒，封面横幅共用一张图，只是尺寸不同。结果文章页顶部直接翻车。

看主题源码，#page-header.post-bg 的高度是写死的：

background-size: cover 和 object-fit: cover 是同一个逻辑：等比铺满、超出裁掉。

于是：

  • 用 630×487 当横幅 → 按宽度铺满 1920px 的屏幕，高度会变成 1483px，实际只显示中间 400px 的一条，图标被裁得只剩中间一小块
  • 用 1600×400 当封面 → 按高度铺满 269px，宽度变成 1076px，塞进 348px 的框里，只剩 32% 的宽度

所以两张图必须分开做。横幅按 1600×400 出图（16:4 = 4:1），在 1920 宽的屏上只裁掉两侧各 160px，图标主体不会受伤。

还有一个更隐蔽的坑：标题重叠区

butterfly 会把文章标题压在横幅的底部。这是 #post-info 的定位决定的：

而标题块的高度取决于标题会不会折行。我用 Playwright 在五个视口下量了主题标题文字的实际包围盒（注意是文字的范围，不是整个 #post-info 容器）：

视口宽 图缩放 标题行数 标题文字上沿（图坐标）
1280 1.00 2 行（长标题） y 214
1280 1.00 1 行 y 266
1440 / 1600 1.00 1 行 y 266
1920 1.20 1 行 y 255
2560 1.60 1 行 y 241

这张表里有个坑：最严格的不是最宽的屏，也不是最窄的屏，而是「窄屏 + 长标题」这个组合。1280 宽时标题折成两行，上沿一下抬到 y 214，比其他所有情况都高。

所以安全下界不能记成一个固定数字，得看你的标题有多长：

  • 标题短（如在 1280 下也是一行）→ 下界 y 245
  • 标题长（1280 下会折两行）→ 下界 y 200

我第一版横幅就是没考虑折行，装饰线画在 y=252，在 1280 下正好压在两行标题上——截图一看就露馅了。

横向也会被裁：x 的安全区

background-size: cover 在两个方向上都可能裁。1600×400 的图铺 1280×400 的容器时，按高度缩放是 1.0，宽度 1600 装不进 1280，于是左右各裁掉 160px：

视口宽 横向裁掉 安全 x 区间（图坐标）
1280 ±160 [160, 1440]
1440 ±80 [80, 1520]
1600 及以上 0 [0, 1600]

这就是为什么横幅的文字起点不能用 x=130——那正好落在 1280 的裁切带里，标题会被切掉一截。起点定在 x=182（160 的安全线再往里让 22px）。

一个更狠的问题：长标题会横向吃掉图标的位置

旧文章的标题短。SnowLuma 那篇在 1440 下标题文字止于 x≈1194，而图标在 x=1110 起——虽然理论上有 84px 重叠，但那个图标是四角星，左下角本来就是空的，压上去看不出来。

但换成实心图标（比如我的 AutoHotkey 方框），同样的重叠就非常刺眼。而长标题更糟：MathInput 那篇标题文字能到 x≈1372，几乎横贯整个画面：

结论：横向是躲不开的，只能把图标和文字一起赶进上方那条安全带。

最终定稿的横幅版式（标题长、会在 1280 折行时用「矮版」）：

元素 矮版（长标题） 常规版（短标题）
主图标 (1120, 100, 96) (1100, 104, 128)
副图标 (1230, 118, 66) (1292, 126, 88)
标题竖条 x=182 y=110 w=5 h=48 x=182 y=112 w=5 h=52
主标题 x=206 y=148 fs=40 x=206 y=152 fs=44
副标题 x=208 y=188 fs=20 x=208 y=194 fs=21

注意两版都没有装饰横线——原来那条 y=238 的线在 1280 下会碰到标题文字，干脆去掉。去掉一个元素比给它找一个永远安全的位置更省事。

四、封面 630×487 的定稿坐标

跑通上面这些之后，我把布局数值固定下来了。所有新文章照抄即可，不要再凭感觉调。

元素 参数
主图标 x=265, y=92, size=175
副图标 x=448, y=180, size=95
标题竖条 rect x=58 y=288 w=6 h=58 rx=3
主标题 text x=82 y=332 font-size=46 font-weight=bold fill=#fff
副标题 text x=84 y=378 font-size=23 fill=accent

关键约束只有一条：图标最低点不得越过 y=288。

92 + 175 = 267，180 + 95 = 275，都在 288 以上，留出 13~21px 的呼吸。这条不是审美问题——图标压到标题线上，缩到 348×269 的卡片里就会糊成一片。

五、横幅 1600×400 的定稿坐标

元素 参数
主图标 x=1120, y=24, size=175
副图标 x=1272, y=116, size=88
标题竖条 rect x=130 y=116 w=6 h=58 rx=3
主标题 text x=158 y=160 font-size=44
副标题 text x=160 y=204 font-size=20
装饰线 line x1=130 y1=238 x2=660 y2=238

左侧文字区从 x=130 开始，图标区从 x=1120 开始，中间留了 500px 的空白。这个空白是有用的：窄屏（比如 1280px 宽的笔记本）下横幅会被裁掉两侧各 160px，此时 x=130 的标题还在，x=1120 的图标也还在。

图标整体比封面靠上：主图标 24 + 175 = 199，副图标 116 + 88 = 204，都在 254 这条线以上。装饰线也从原来的 252 提到 238，就是为了躲开标题区。

注意图标比封面小了一圈（175 vs 185）。这不是随便缩的：横幅里留给图标的垂直空间只有 y<254 这 254px，再扣掉上下留白，180 已经是上限，再大就会顶到标题。

六、两个图标的分工

每条封面上都有两个图标。它们不是「找两个好看的凑一起」。

主图标 = 文章主题的官方矢量图。 讲 Docker 就放 Docker 官方图标，讲 AutoHotkey 就放 AHK 官方图标。必须是原版，不能自己重画、不能用第三方再创作的版本。

副图标 = 这篇文章对该主题做了什么。 我固定用一个「魔法棒」：

用同一篇文章的旧版对比一下，差别就更明显了——旧版尺寸对、也没越线，但三根色条什么也没说：

语义是改造 / 修补 / 自定义——讲怎么把官方机器人换成自建，讲怎么给输入法补一个缺失的能力，都是「改造」。同一语义用同一个形状，读者扫一眼首页就知道这类文章是「折腾记录」。

这条规则踩过坑。之前有一篇写 SnowLuma 的，副图标我放了 SnowLuma 的官方 favicon，被用户直接否了——理由是「favicon 不是 logo，而且跟这篇文章讲的『放弃官方方案』毫无关系」。后来换成雪花（SnowLuma 的品牌元素），语义才对上。

判断标准：副图标要选和本文动作对应的形状，而不是「这个项目还有哪些图标没用过」。

七、素材从哪来

优先级从高到低：

  1. 用户自己手上的官方 SVG。改 Win11 任务栏那篇，徽标、魔法棒、刷新箭头全是用户从系统里导出的原版
  2. simple-icons 官方仓库。https://raw.githubusercontent.com/simple-icons/simple-icons/develop/icons/<name>.svg，Docker、Laravel、Ubuntu、AutoHotkey、Hexo 都有，MIT 协议，直接 curl 下来
  3. 项目自己仓库里的 logo。AstrBot 的 docs/public/favicon.svg 就比 favicon.ico 靠谱

八、生成脚本长什么样

整套东西是一个不到 120 行的 Node 脚本，不依赖任何图形库——直接拼 SVG 字符串。

place 里那段 vx/vy 偏移是必须的：simple-icons 全是 viewBox="0 0 24 24"，但用户给的图标经常是 viewBox="0 0 1024 1024" 里只画了右上角一小块——非零原点的 viewBox 如果不做平移，图标会整个跑到画布外面。

九、怎么验收（这一步最费时间）

SVG 写完不能只看代码，必须渲染出来目检。而且不能只看原尺寸——要按它真实的显示尺寸看。

我的验收脚本做三件事：

  1. 630×487 原尺寸：检查整体构图
  2. 348×269 缩放版：模拟首页卡片实际显示，检查缩到 40% 后文字还认不认得出
  3. 1600×400 横幅：直接按原尺寸截

第 2 步是关键。很多在 630×487 下看着舒展的布局，缩到 348×269 之后副标题就模糊了——因为字太小。副标题 23px 缩到 348 宽时只剩 12.7px，这是下限，不能再小。

十、迭代规则（血泪版）

这是六轮目检之后才总结出来的，每条都对应一次返工：

① 一次只走 ±30px 量级。 早期我一次调 80px，直接调过头，又得往回找。小幅步进才能收敛。

② 封面和横幅必须分开调。 有一轮我「统一」把两者都下移，封面下移 30px、横幅下移 38px，结果用户判定横幅过了、封面刚好——于是只能把横幅单独回退 38px。绑在一起改 = 一起返工。

③ 目检顺序：先封面，后横幅。 首页缩略图的曝光权重最高，它不对，横幅再好看也没用。

④ 用户说「靠上/分太开/关联性不足」时，先量数值再改。 这几种反馈都不是审美问题，是坐标问题。把图标包围盒算出来，比对安全线，往往能直接定位。

十一、这套规则的边界

说清楚它不适合什么：

  • 只适用于 butterfly 主题。换主题，.post_cover 的 42%/16.8em 和 #page-header 的 400px 全都变了，整套数值作废
  • 只适用于图右文左/图上文下的固定版式。如果要放照片、要放截图，这套「图标 + 双行文字」的模板就不够了
  • SVG 里烘焙的文字改不了。文章标题一旦改名，封面上的文字要重新生成。这也是为什么我把标题做成脚本里的常量，而不是设计文件
  • 字体依赖系统。SVG 里写的是 Microsoft YaHei, PingFang SC, sans-serif，在没装这些字体的机器上渲染（比如 CI）会 fallback，字宽会变

如果要跨平台稳定，得把文字转成 path，或者直接在构建时截图成 PNG。

最后

这套东西的价值不在「好看」，在于可复现。

以前每写一篇，封面都要现调半小时：试尺寸、试位置、被裁切、再改。现在只要填三个常量（标题、副标题、主图标路径），跑一次脚本，出两张图，坐标全对。

设计这件事，能被写成数字的部分就应该写成数字。剩下的那点审美，才值得花时间。
