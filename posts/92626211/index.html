先说结论

NAS 放在家里，人在公司、在手机流量下、在出差酒店，随时都要能打开它读写文件。这件事的最初解法是 nps 做端口转发，卡在那台 3M 带宽的云服务器上；换成 P2P 打洞之后，公网服务器只负责握手、数据两端直连；再给发送端换一个拥塞控制算法，同一个 3.89 GB 文件从 3 小时压到 13 分钟。

三个阶段的实际速度，同一台 NAS、同一个文件：

方案 稳定速度 传完 3.89 GB
nps 中转，云服务器 3M 带宽 375 KB/s 约 3 小时
Tailscale 打洞直连，系统默认 CUBIC 652 KB/s 约 1 小时 45 分
Tailscale 直连 + BBR 4.90 MB/s 约 13 分钟

两次提速对应两个不同的瓶颈，这也是全文的主线：

  • 第一步（375 → 652 KB/s）换的是路径。 数据不再经过那台 3M 云服务器，改走两端直连。
  • 第二步（652 KB/s → 4.9 MB/s）换的是算法。 路径已经是最优的 26 ms 直连、0 丢包，但发送端用 CUBIC，在 3–5% 丢包的链路上把单条 TCP 流锁死在 5 Mbps。

组网工具决定「走哪条路」，拥塞控制决定「这条路能跑多快」。路径选对了、算法不对，速度照样上不去。

一、需求不是把 NAS 暴露到公网

先把问题界定清楚，后面每一步才有判断依据。

NAS 在家里的内网，192.168.10.77，从这个局域网之外的地方根本路由不到。要的效果只有一条：在任何一个有网的地方，用浏览器或资源管理器打开它，像访问本地磁盘一样。

最直觉的做法是端口映射——把 NAS 的端口直接映射到公网 IP。这条路走不通，有两个原因：

  • 家宽普遍封 80/443，绝大多数服务架不起来
  • 端口一旦映射出去，就等于把管理后台交给全网扫描器，登录框每天被爆破

所以只剩两类做法：走一条加密隧道（两端各装客户端，公网只做协助），或者走一个中转（访问者直接连中转机，中转机再去取数据）。最初选的是后者，也就是 nps。

二、先用的是 nps，卡在那台 3M 云服务器上

nps 的 server 端跑在云服务器上，client 端跑在 NAS 上，外面通过云服务器的地址访问。配置直观，一条端口映射对应一个服务，用起来没门槛。

代价在流量模型上：访问者 → 云服务器 → NAS，两段都经过同一台机器。这台机器的带宽就是天花板，跟两端家里的真实带宽没有关系。

我的云服务器是 3M 带宽。3M 换算过来 375 KB/s，实测也就是这个数，一分不多一分不少。

用途 3M（375 KB/s）够不够
SSH、Web 管理后台 够，操作没有明显等待
传文件 / 备份 不够，1 GB 要 45 分钟
看 NAS 里的视频 不够，低码率也卡
远程桌面 勉强，得降色深、关动画

问题不在 nps 写得不好，而在中转这个模型本身：它把「访问速度」和「中转机带宽」绑死了。升级中转机是一条路，但云服务器 3M 提到 10M 一个月多几十块，而且带宽永远追不上家宽。

真正该改的是模型，不是配置。

三、换思路：让公网服务器只做握手

如果两端能互相发包，数据就没必要绕路。P2P 打洞（NAT 穿透）做的就是这件事。

原理一层就够：两台机器各自先从内网发一个包到公网上的 STUN／信令服务，服务记录下它们各自的公网出口 IP:端口；然后把对方的出口地址告诉它。双方拿到地址后同时向对方的外网出口发包，路由器看到「内网刚发出去过、回包正好回来」，就把这条映射放行。通道建立之后，信令服务完全不参与数据传输。

公网服务器的角色，从「数据中转」降级成「地址交换」。它只要活着、能回几个几十字节的包就够了。

nps 中转 P2P 打洞
数据路径 两端都绕云服务器 两端直连
速度上限 中转机带宽（3M） 两端带宽的较小值
中转机负载 每字节都过 仅握手阶段的信令
中转机挂掉 立刻不可用 已建立的连接不受影响
代价 配置简单 依赖 NAT 类型，可能打不通

打洞不是万能的。三种情况会失败：一端是对称型 NAT（每个目标分配不同端口，无法预测）、链路上封 UDP（企业网、校园网常见）、双层 NAT 让映射不稳定。

这三条都可以在动手前查出来，所以安装之前先做一轮网络环境确认——见第五节。

这一节还留下一个预期：直连之后，速度应该等于两端带宽的较小值。 记住这句话，第八节会拿它当靶子。

四、P2P 方案里为什么选 Tailscale

能打的洞都是同一个洞，差别在客户端成熟度和「打不通时怎么办」。

方案 优势 短板
Tailscale 客户端最成熟，装完扫码即用；打洞失败自动降级到 DERP 中继，几乎不会完全连不上；MagicDNS、子网路由、exit node 齐全 控制面闭源且在境外，首次登录要能访问；默认中继节点在境外，延迟高
ZeroTier 唯一支持二层：广播、组播、mDNS、网上邻居、老游戏联机 非 WireGuard，包头开销大，同链路吞吐偏低；免费 25 设备；新设备要手动授权
EasyTier 无控制面，约定网络名 + 密钥即可；Rust 单二进制，OpenWrt 有 ipk；抗丢包做得好 生态较新，公共中继由社区提供，中继时流量过他人机器
frp xtcp 已有 frp 的话迁移成本最低，服务端只辅助打洞 需要自备服务端和配置，没有自动降级
nps 的 p2p 模式 不用换工具 文档零散，各版本行为不一致，排障成本高

选 Tailscale 的理由不是它最快——数据面都是 WireGuard，同一链路上差不了几个百分点——而是它的失败路径最体面：打洞成功走直连，打洞失败退到中继，永远有一个能用的结果，不会出现「装完发现连不上」。

这个选择的代价也要认：控制面在境外，首次登录必须能访问 login.tailscale.com。没有代理的话，第一步就过不去。

六、安装：Docker 还是命令行

NAS 是飞牛 fnOS（Debian 12），两种方式都能用，但条件完全不同。

两种方式的差异

Docker 命令行（apt / 官方脚本）
安装量 一个 compose 文件 三条命令，systemd 托管
权限面 容器要 NET_ADMIN + NET_RAW + /dev/net/tun 直接是 root 服务，权限本来就是它的
网络模式 必须 network_mode: host，否则打洞必失败 天然宿主网络
状态持久化 要挂 /var/lib/tailscale，否则容器重建就掉登录 在 /var/lib/tailscale，升级不影响
与其他容器互通 其他容器要走 Tailscale 网络，得额外开 ip_forward tun0 是系统级设备，全部容器直接可达
升级 拉新镜像重建容器 apt upgrade
卸载 删容器和目录 apt remove tailscale，干净
适合 不想动系统目录、要和其他 compose 服务放一起管 想少一层、少一处出错点

那张表里只有一行是硬约束：network_mode: host 不能省。默认的 bridge 网络下，容器看不到宿主真实网络，打洞必然失败，NAS 上的服务也访问不到。

我最后用的是命令行版。 三个理由，都在表里：

  1. tun0 是系统级设备，飞牛面板、Samba、其他 Docker 容器全部直接可达，不用再为容器互通加转发规则
  2. 不需要给容器额外放大权限，少一处可以被配置错的地方
  3. 卸载干净，apt remove 就结束

只有一种情况选 Docker：你已经习惯用 compose 管所有服务，希望 Tailscale 和其他容器放一起启停，或者不愿意往系统目录里装东西。

八、测速度：直连只有 652 KB/s

ping 只测延迟，真实吞吐得传大文件。最省事的是 SMB：资源管理器地址栏输入 \\100.125.162.49，拖一个 3.89 GB 的文件过去。

结果是 652 KB/s，1 小时 45 分。比 nps 的 375 KB/s 快了不到一倍，离「直连等于带宽」差得远。

这时候很容易得出「Tailscale 不行」的结论。先别急，把「慢」拆成三层，一层层排除：磁盘、链路、协议。

第一层：磁盘是不是瓶颈

607 MB/s，机械盘和 SATA SSD 都给不出这个数，是写在缓存层的。总之不是瓶颈。

第二层：链路是不是丢包、是不是被代理劫持

ping 用 1200 字节，接近隧道 MTU，比默认 32 字节有意义得多。实测 12 个包 0% 丢包、抖动 4 ms；tracert 只有一跳，直接就是 NAS 的 Tailscale 地址，说明没有代理在中间劫持。

第三层：是不是 SMB 协议的问题

换一个协议做对照。NAS 上起个 HTTP 服务，从 Windows 用 curl 拉同一个文件：

HTTP 478 KB/s，同期 SMB 548 KB/s。两个数与开头的 652 KB/s 差在同一量级的采样波动上（缓存预热、单次计时），关键是「两条路径同速」这个形态——SMB 协议被排除。如果 HTTP 能跑满而 SMB 不行，问题才在 Samba 配置。

三层排除完，结果摆在一起：

检查项 结果 结论
磁盘 607 MB/s 排除
1200 字节包丢包率 0% 链路质量好
延迟抖动 26–30 ms 稳定
tracert 跳数 1 跳 无代理劫持
HTTP over 隧道 478 KB/s 排除 SMB 协议
实际吞吐 478–652 KB/s 问题在这一层

磁盘、链路、协议全部健康，数据却只能跑 4 Mbps 左右。剩下的怀疑对象只有一个：带宽真的只有这么点。

九、定位：单流被 CUBIC 锁死在 5 Mbps

「带宽只有这么点」这个判断，被一个数字误导过：speedtest-cli 报上行 4.06 Mbps，看着结论很明确。

换成 iperf3 打四条并行流，同一时间、同一条上行：

测法 吞吐 说明
speedtest-cli（单流） 4.06 Mbps 这是单流上限，不是带宽上限
iperf3 -P 4（四流） 20.8 Mbps 真实上行至少 20 Mbps
四流中的每一条 5.1–5.4 Mbps 被同一个数字锁住

四条流各自 5.1–5.4 Mbps、总和 20.8 Mbps。这个形态说明瓶颈不在总带宽，而在单条流始终爬不上去。

单流上限可以算出来。RTT 26 ms、丢包率约 1%、MSS 1460 字节：

和实测完全对得上。这不是巧合，是 CUBIC 的吞吐公式。

同一次输出里还有两个指标，比吞吐更有说服力。先解释一下拥塞窗口（Cwnd）是什么：可以理解为「在收到对方确认之前，一次最多能发多少数据」。窗口越大，单位时间发得越多；窗口被压小，链路再空也发不快。

指标 实测 正常值 含义
Cwnd 拥塞窗口 2.7 KB – 20.5 KB 26 ms 下应到 100 KB+ 窗口只有正常的零头
Retr 重传 约 200 次 / 条 / 8.8 秒 个位数 持续丢包，反复退回慢启动

CUBIC 的规则是丢包就往回缩。窗口缩了吞吐就低，吞吐低就更难探到可用带宽。这也解释了为什么「延迟 26 ms、ping 0% 丢包」的链路实际只有 500 KB/s——ping 发的是小包、速率极低，测不出上行整形器在高负载下的丢包。

单流测速工具（speedtest、单个 curl、单次 SMB 复制）测的是算法天花板，不是物理带宽。判断家宽上行，必须跑多流。

十、开 BBR：路径不变，换算法

BBR 是 Google 提的一种拥塞控制算法。 它不看丢包判断拥塞，而是持续估算「这条链路当前能跑多快」和「往返延迟有多久」，按估算值控制发包节奏。所以链路上有 3–5% 丢包时，CUBIC 会一路缩窗口，BBR 却能把丢掉的包吞下去继续推。

Debian 12 内核自带 BBR，不需要装模块。NAS 是数据发送方，改发送端才有意义。

fq 不是可选项。BBR 依赖这个队列调度器控制发包节奏，配成 pfifo_fast 吞吐会明显打折。

验证别用 sysctl 命令。 普通用户的 PATH 里没有 /usr/sbin，sysctl -p 之后紧接着敲 sysctl net.ipv4... 会报 command not found，看着像失败，其实已经生效。直接读 /proc/sys/ 下的文件最可靠。

效果，同一条链路、同一台 NAS 作发送端：

指标 CUBIC BBR 变化
四流总和 20.8 Mbps 49.1 Mbps +136%
单流 5.1–5.4 Mbps 12.1–12.5 Mbps +130%
拥塞窗口 2–20 KB 100 KB+ 约 5 倍

49.1 Mbps 这个数字很接近 50M 整数，说明上行本身可能有 50M 的整形上限，BBR 已经把能拿到的都拿到了。

验证时最容易踩的坑：旧连接不走新算法

改完 BBR，curl 立刻变成 4.77 MB/s，SMB 复制还是 652 KB/s。这不是 BBR 没生效，是那条 SMB 会话在改配置之前就建立了。

拥塞控制只对新建连接生效。 而 Windows 的 SMB 客户端是按服务器名缓存会话的：

断开方式 结果
net use * /delete /y 无效——地址栏敲 UNC 是隐式连接，没有显式映射可删
Restart-Service LanmanWorkstation -Force 可能失败——依赖 Browser 服务，停不掉就整体失败
换一个访问名（IP → 完整域名） 立即新建会话，生效
访问方式 速度
\\100.125.162.49（改 BBR 前建立的会话） 652 KB/s
\\fn-8100t.tailf92ed3.ts.net（新会话） 4.90 MB/s

改完任何网络栈参数（拥塞控制、MTU、缓冲区），第一件事是断开旧连接再测。 这类配置对已建立的连接一律无效，测出来的全是上一轮的数字。

最后落到实际使用

层 数值 说明
家宽上行（电信 → 云服务器 BGP） 49.1 Mbps iperf3 多流实测
Tailscale 实测（电信 → 联通，P2P 直连） 39 Mbps / 4.90 MB/s 效率 77%
损耗构成 WireGuard 加密 + UDP 封装 + 跨网丢包 正常范围

77% 对跨网 P2P 加密隧道是健康水平，剩下 23% 主要是加密与封装的固有开销，配置层面改不动。

BBR 的代价

两个代价要认：

  • 对同链路其他流量不够友好。 BBR 流会持续抢占，同链路上的 CUBIC 流被挤压。家宽只自己在用没有影响，共享上行时要考虑。
  • 丢包不会消失。 3–5% 的丢包被吞下去了，重传仍然发生，有效带宽比理论值低两成左右。这部分损耗换任何算法都消不掉。

十一、定稿：让它开机就绪

服务能用之后，把它固定下来，避免每次重启都要重新配。

三个容易做错的地方：

IP 和域名是两条独立凭据。 用 100.125.162.49 认证过，不代表域名也认证过。cmdkey 的 target 必须和映射时用的名字完全一致，且不带 \ 前缀。

net view 在这台机器上用不了。 它对服务器做匿名枚举，飞牛 / Samba 默认拒绝，返回「系统错误 5 拒绝访问」。这不是密码错——密码错是错误 1326。另外它只接受服务器名，传 \\server\share 会返回错误 53。要看共享列表，直接在资源管理器地址栏敲 \\fn-8100t.tailf92ed3.ts.net，走已认证会话。

优先用完整域名，不用短名。 短名依赖 DNS search domain，代理或 DNS 一变就解析失败；完整域名只依赖 MagicDNS。

安全提示：cmdkey 存的凭据按 Windows 用户加密（DPAPI），同机其他用户读不到，但当前用户可以在「控制面板 → 凭据管理器 → Windows 凭据」点「显示」看到明文。 在公司电脑上存私人 NAS 密码，等于把密码留在这台机器上。如果这台机器会借给别人、或做过整盘镜像，就不该保存。

最后是代理规则。Clash 的 TUN 模式会劫持所有出站流量，包括 100.64.0.0/10——Tailscale 的 CGNAT 网段。被劫持后的表现很迷惑：能 ping 通、能连上，但速度掉到几百 KB/s。

no-resolve 不能省。少了它，规则匹配时会对 100.64.0.0/10 里的每个地址发起 DNS 查询，把 MagicDNS 一起卷进去。

十二、易错清单

现象 原因 处理
NatTypeTester 报 GLIBC_2.38 not found Debian 12 只有 2.36 换 pystun3，或用 --network host 的容器
容器里测出对称型 NAT 忘了 network_mode: host 加 --network host，bridge 网络测的是容器自己的 NAT

流程速查

最后：一个判断表，省掉下一次排查

这套东西的价值不在于换了个工具，而在于把「慢」拆成了可以分别验证的三层，每一层对应一种改法：

症状 瓶颈在哪 该动什么
单流、多流一样慢，换个中转也一样 物理带宽 提带宽，或换一条路径
多流快、单流慢 拥塞控制算法 换算法（BBR），换工具没用
时通时断、握手就失败 NAT 类型或防火墙 回到第五节确认网络环境
能连上但速度只有几百 KB/s，且开着代理 流量被劫持 加 DIRECT 规则

我这次撞的是第二行，却先误判成第一行——speedtest 报 4 Mbps 时差点直接去找运营商提带宽。判据其实一句话：多流能跑满、单流跑不满，就是算法问题，不是带宽问题。

先测清楚瓶颈在哪一层，再决定改什么。改错层，所有操作都是零收益。

还剩一件事没做：netcheck 显示最近的 DERP 节点是旧金山 159 ms，香港反而 213 ms。平时打洞成功用不上它，但万一哪天打洞失败退回中转，延迟会很痛苦。那台已经闲置的 3M 云服务器做自建 DERP 正合适——只在中转时吃流量，3M 兜底够用，延迟能压到 30 ms 内。这部分留到下一篇。
