异地访问 NAS：从 3M 中转到 4.9 MB/s

发表于2026-11-23|更新于2026-11-23|折腾记录
|浏览量:

先说结论

同一台 NAS、同一个 3.89 GB 文件，三个阶段的实际速度：

方案 稳定速度 传完 3.89 GB
nps 中转，云服务器 3M 带宽 375 KB/s 约 3 小时
Tailscale 直连，系统默认 CUBIC 652 KB/s 约 1 小时 45 分
Tailscale 直连 + BBR 4.90 MB/s 约 13 分钟

链路质量全程是健康的：直连延迟 26 ms、1200 字节包 0% 丢包、NAS 本地磁盘 607 MB/s、tracert 只有一跳（没有代理劫持）。限制速度的不是路径，是发送端的拥塞控制算法。

Debian 12 默认用 CUBIC。它把丢包当作拥塞信号，在这条上行丢包率 3–5% 的链路上，单条 TCP 流被压在 5 Mbps 上下，客户端怎么重试都上不去。换 BBR 之后，同一条链路单流从 5.4 Mbps 提到 12.4 Mbps，四条并行流的总量从 20.8 Mbps 提到 49.1 Mbps。

组网工具决定「走哪条路」，拥塞控制决定「这条路能跑多快」。路径选对了，算法不对，速度一样上不去。

一、单流测速会把上行报低一半以上

最初的判断是被一个数字误导的：speedtest-cli 报上行 4.06 Mbps，看起来结论很明确——家宽上行只有 4M。这个结论是错的。

换成 iperf3 打四条并行流，同一时间、同一条上行：

测法 吞吐 说明
speedtest-cli（单流） 4.06 Mbps 这是单流上限，不是带宽上限
iperf3 -P 4（四流） 20.8 Mbps 真实上行至少 20 Mbps
四流中的每一条 5.1–5.4 Mbps 被同一个数字锁住

四条流各自 5.1–5.4 Mbps、总和 20.8 Mbps，这个形态说明瓶颈不在总带宽，而在单条流始终爬不上去。

单流上限可以估算。RTT 26 ms、丢包率约 1%、MSS 1460 字节：

和实测的 5.1–5.4 Mbps 完全对得上。这不是巧合，是 CUBIC 的吞吐公式。

单流测速工具（speedtest、单个 curl、单次 SMB 复制）测的是算法天花板，不是物理带宽。判断家宽上行，必须跑多流。

二、两条硬证据：窗口没长起来，重传却大量发生

同一次 iperf3 输出里还有两个指标，比吞吐数字更有说服力：

指标 实测 正常值 含义
Cwnd 拥塞窗口 2.7 KB – 20.5 KB 26 ms 下应到 100 KB+ 窗口只有正常的零头
Retr 重传 约 200 次 / 条 / 8 秒 个位数 持续丢包，反复退回慢启动

CUBIC 的规则是丢包就往回缩。窗口缩了吞吐就低，吞吐低就发不快，链路利用率只有 10%。这解释了为什么「延迟 26 ms、ping 丢包 0%」的链路，实际传输只有 500 KB/s——ping 发的是小包且速率极低，测不出上行整形器丢包。

三、开 BBR：三条命令，立即生效

Debian 12 内核自带 BBR，不需要装任何模块。

fq 不是可选项。BBR 依赖这个队列调度器做发包节奏控制，配成 pfifo_fast 或没有 fq 时，吞吐会明显打折。

验证别用 sysctl 命令。 普通用户的 PATH 里没有 /usr/sbin，sysctl -p 之后紧接着敲 sysctl net.ipv4... 会报 command not found，看着像失败，其实已经生效。直接读 /proc/sys/ 下的文件最可靠。

效果（同一条链路、同一台 NAS 作为发送端）：

指标 CUBIC BBR 变化
四流总和 20.8 Mbps 49.1 Mbps +136%
单流 5.1–5.4 Mbps 12.1–12.5 Mbps +130%
拥塞窗口 2–20 KB 100 KB+ 约 5 倍

49.1 Mbps 这个数字很接近 50M 整数，说明上行本身可能就有 50M 的整形上限，BBR 已经把能拿的都拿到了。

四、BBR 的代价要认

BBR 不把丢包当拥塞信号，只看 RTT 和带宽估计模型。代价有两个：

  • 对同链路其他流量不够友好。 BBR 流会持续抢占，同一链路上的 CUBIC 流被挤压。家宽只自己在用，没有影响；共享上行时要考虑。
  • 丢包不会消失。 BBR 把 3–5% 的丢包吞下去了，但重传仍然发生，实际有效带宽比理论值低两成左右。这部分损耗换任何算法都消不掉，除非改善链路本身。

五、Tailscale 的效率：39 Mbps / 49 Mbps = 77%

开 BBR 后，从 Windows 通过 Tailscale 拉同一个文件：

层 数值 说明
家宽上行（电信 → 阿里云 BGP） 49.1 Mbps iperf3 多流实测
Tailscale 实测（电信 → 联通，P2P 直连） 39 Mbps / 4.9 MB/s 效率 77%
损耗构成 WireGuard 加密 + UDP 封装 + 跨网丢包 正常范围

77% 对跨网 P2P 加密隧道是健康水平。剩下 23% 主要是加密与封装的固有开销，不是配置能改的。

六、SMB 老连接会沿用旧算法，这是最容易误判的一环

BBR 生效之后，HTTP 下载立刻变成 4.77 MB/s，SMB 复制还是 652 KB/s。

原因：拥塞控制只对新建立的连接生效。 SMB 那条会话是改配置之前建立的，全程跑着 CUBIC。

问题在于断开连接没想象中容易。Windows 的 SMB 客户端按服务器名缓存会话：

操作 结果
net use * /delete /y 无效——直接在资源管理器敲 UNC 路径是隐式连接，没有显式映射可删
Restart-Service LanmanWorkstation -Force 可能失败——依赖 Browser 服务，停不掉就整体失败
换一个访问名（IP → 完整域名） 立即新建会话，生效

实测对照：

访问方式 速度
\\100.125.162.49（改 BBR 前建立的会话） 652 KB/s
\\fn-8100t.tailf92ed3.ts.net（新会话） 4.90 MB/s

调整任何网络栈参数（拥塞控制、MTU、缓冲区）之后，第一件事是断开旧连接。 这类配置对已建立的连接一律无效，测出来的数字全是上一轮的。

七、映射成盘符，并把凭据存对

三个容易做错的地方：

IP 和域名是两条独立凭据。 用 100.125.162.49 认证过，不代表域名也认证过。cmdkey 的 target 必须和映射时用的名字完全一致，且不带 \\ 前缀。

net view 在这里用不了。 它对服务器做匿名枚举，飞牛 / Samba 默认拒绝，返回「系统错误 5 拒绝访问」。这不是密码错——密码错是错误 1326。另外 net view 只接受服务器名，传 \\server\share 会返回错误 53。

共享名从资源管理器看。 地址栏输入 \\fn-8100t.tailf92ed3.ts.net（不带共享名），回车后能看到全部共享。

安全提示：cmdkey 存的凭据按 Windows 用户加密（DPAPI），同机其他用户读不到，但当前用户可以在「控制面板 → 凭据管理器 → Windows 凭据」点「显示」看到明文。 在公司电脑上存私人 NAS 密码，等于把密码留在这台机器上。如果这台机器会借给别人、或做过整盘镜像，就不该保存。

八、代理必须放行 Tailscale 网段

Clash 这类工具的 TUN 模式会劫持所有出站流量，包括 100.64.0.0/10——Tailscale 的 CGNAT 网段。被劫持后的表现很迷惑：能 ping 通、能连上，但速度掉到几百 KB/s，因为流量绕道去了代理节点。

规则要排在前面：

no-resolve 不能省。少了它，规则匹配时会对 100.64.0.0/10 里的每个地址发起 DNS 查询，把 MagicDNS 一起卷进去。

首次登录需要能访问官方控制面。这一步如果失败，先关代理完成登录，成功后再开——P2P 建立之后，日常通信不需要控制面参与。

九、易错清单

现象 原因 处理
speedtest 报上行 4M，实际不止 单流测速测的是算法上限 iperf3 -c IP -P 4 多流复测
延迟低、ping 0 丢包，速度只有 500 KB/s CUBIC 在小丢包链路上锁死单流 发送端开 BBR
开了 BBR，测速工具变快但复制没变 老连接沿用旧算法 断开旧会话，或换访问名强制新建
sysctl 报 command not found /usr/sbin 不在普通用户 PATH 读 /proc/sys/... 验证
net view 报错误 5 Samba 禁止匿名枚举 用资源管理器浏览共享
重启后仍弹密码框 /persistent:yes 只保证重连，不存密码 补 cmdkey /add
开代理后速度骤降 TUN 劫持了 100.64.0.0/10 规则加 DIRECT
直连偶尔退回中转，延迟暴涨 走的是境外 DERP 节点 自建 DERP 兜底（见下篇）

完整流程速查

最后

这次排查真正改变的不是工具，是判断方法。

「换个组网工具能不能更快」这个问题，答案取决于瓶颈在哪一层：

  • 瓶颈在中转服务器带宽 → 换 P2P 直连（第一步，375 → 652 KB/s）
  • 瓶颈在家宽上行 → 换什么都不行，只能找运营商提带宽
  • 瓶颈在拥塞控制算法 → 换工具、换协议都没用，必须改算法（第二步，652 KB/s → 4.9 MB/s）

拿单流测速去判断带宽，会把第三种误判成第二种，然后开始怀疑每一个工具。多流压测，加上 /proc 里那两个数字，比任何横向评测都直接。

先测清楚瓶颈在哪一层，再决定改什么。改错层，所有操作都是零收益。
