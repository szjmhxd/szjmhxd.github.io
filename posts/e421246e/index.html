AstrBot + SnowLuma 部署实录：一次把方向搞反的 WebSocket 排查

背景

目标很简单：在 NAS 上跑一个 QQ 机器人，用大模型接话。

拆成两半：

  • AstrBot —— 大模型对话框架，负责调模型、跑插件、管人设。
  • SnowLuma —— QQ 协议端，通过 ptrace 注入 QQ 客户端进程，把 QQ 包装成 OneBot v11 接口。

两半之间用 WebSocket 连。听起来是标准动作，实际折腾了一个多小时，全部时间都耗在一个方向上。

下面所有命令都在 NAS 的 SSH 里执行，前提是已经装好 Docker 和 Compose 插件。

一、先搞清楚谁连谁

这是整篇文章唯一值得先记住的事：

AstrBot 的 OneBot v11 适配器（aiocqhttp）只会当反向 WebSocket 服务端，它没有主动外连别人的能力。

所以下面这条是错的：

正确的是反过来的：

我刚上手时看到 SnowLuma 的 OneBot 配置页里有个 ws-default 0.0.0.0:3001 的服务端，就想当然地以为「既然它有 WS 服务端，那就让 AstrBot 去连它」。结果 AstrBot 的表单里根本没有「主动连接」这一项 —— 它只有「反向 WebSocket 主机 / 端口 / Token」。

这个认知偏差是多花了一个小时的根本原因。判断依据很简单：看哪一端有「填写别人的地址」的输入框，哪一端就是客户端。 SnowLuma 的「WS 客户端」页能让填 URL，它才是客户端。

二、整体架构

数据流一句话：QQ ← 进程注入 ← SnowLuma ←WS→ AstrBot → 大模型 API。

端口分工：

端口 归属 用途 是否映射到宿主机
6185 AstrBot WebUI 管理面板 是
6199 AstrBot OneBot v11 反向 WS 服务端 否（走 docker 内网）
6081 SnowLuma noVNC 远程桌面，扫码登录用 是
5099 SnowLuma SnowLuma WebUI 是
3000 / 3001 SnowLuma OneBot HTTP / WS 服务端 否（本方案用不到）

注意最后一行：SnowLuma 自带的 3000/3001 在反向 WS 方案里完全不需要暴露。少开两个口，就少两个被扫的入口。

九、踩过的坑

1. docker compose build 卡住，其实什么都没做

现象：命令跑完没有任何输出，以为卡死了。

原因：compose 文件里只有 image: 没有 build: 段，build 是空操作，直接返回 0。真正耗时的是 docker compose up -d 在拉镜像（约 2GB）。

3. 401 Unauthorized 被误判成失败

现象：用 curl 测端口，返回：

第一反应是「端口有问题」。恰恰相反，这是端口完全正常的证据。 没带 token 被拒绝，说明 TCP 通了、HTTP 通了、WS 路由也在。如果端口没开，看到的会是 Connection refused 或超时，根本不会有这个响应。

判读口诀：

返回 含义
401 服务正常，只是 token 不对
Connection refused 端口没映射到宿主机
超时 被防火墙/安全组拦了

4. wsClients 是空数组，却一直去查端口

现象：AstrBot 显示 adapter 加载成功但没有「已连接」。

原因：SnowLuma 的配置里 "wsClients": [] —— 客户端压根没创建过，根本没发起连接。查端口是在查一个不存在的问题。

看到 "wsClients": [] 就别再折腾端口了，去 WebUI 的「WS 客户端」页新建。

另外注意 "mode": "overlay" 时，账号级文件 onebot_<uin>.json 会覆盖基础文件 onebot.json，光改一个可能不生效。用 WebUI 保存最稳妥，应用会自己落盘。

5. 容器里没有 ss / netstat

现象：sh: 1: ss: not found。

6. 别照抄别人的教程

踩到两处：

  • 某教程的 SnowLuma 卷路径写的是 /app/snowluma-data，官方文档是 /app/data。照抄的话配置和登录态会存进一个没人读的目录，重启全丢。
  • 某教程写 URL 用「ws://AstrBotDocker网段:6199/ws」，这是占位符，不是真的让你填网段。填容器名 astrbot 或具体容器 IP。

7. docker network connect 不持久化

容器一被重建（docker compose up -d 检测到 compose 变化就会重建），手动 connect 的网络连接就丢了，连接器又变回连不上。

十、安全

这套组合的风险点和普通 Web 服务不一样，6081 尤其要当心：

  • 6081 等于一台能操作你 QQ 的远程桌面。 端口一暴露，扫到的人可以直接接管你的号。别裸放公网，要远程就套反代加认证，或者走 Tailscale / WireGuard。
  • 6199 不映射宿主机，只在 botnet 内网可见。这是本方案比「映射到宿主机」更好的地方。
  • Token 不要留空（前提是端口映射过）。留空等于允许任何能连上该端口的人接入你的机器人。
  • 登录态卷别删。 share 卷存的是 QQ 登录态，删了要重新扫码。

小结

技术上没有难点，全程卡在一个方向性误判上 —— 看到 SnowLuma 有 WS 服务端就以为该让它当服务端。真正的判断依据不在功能列表里，而在「哪一端需要填对方的地址」。

如果把这次的经验浓缩成三句话：

  1. 反向 WS 意味着「被动方」是服务端，它永远不会主动找你。
  2. 先验证网络层（TCP 能不能通），再动配置。 顺序反了会浪费大量时间在错误的地方找原因。
  3. 401 是好消息，Connection refused 才是问题。
