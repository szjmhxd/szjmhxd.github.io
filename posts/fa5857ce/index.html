MediaShelf：把混乱的本地影视库整理成刮削器认得的结构

发表于2026-11-27|更新于2026-11-27|开发工具
|浏览量:

下载的影视资源，文件名是发布组的命名习惯：长发公主.Tangled.2010.BluRay.1080p.x265.10bit.3Audio.MNHD-FRDS.mkv、01.flv、2026-07-25 第5期上.mkv。Jellyfin/Emby 的刮削器按「片名 (年份)」去 TMDB 找条目，文件名对不上就识别不出，海报、简介、评分全是空的。手工改 50 个文件还能忍，改 2000 个就是另一回事。

MediaShelf 是一个开源的 Windows 桌面工具（Python + PySide6），把「扫描 → 联网识别 → 预览 → 执行」做成一条流水线：读 TMDB 元数据，按你定的命名模板改名、归目录、生成 nfo 和海报。电影、剧集、综艺三类都覆盖。本文是它的匹配引擎设计与 2000+ 文件整理的实测记录。

源码与下载：github.com/szjmhxd/media-shelf

目标结构：让刮削器一眼认出

整理的终点是 Jellyfin/Emby 惯例的目录布局：

类型 目录结构 示例
电影（无系列） 片名 (年)/片名.英文名.年份.片源….mkv 天气之子 (2019)/天气之子.天気の子.2019.BluRay….mkv
电影（有系列） Xxx Collection/片名 (年)/… 冰雪奇缘 Collection/冰雪奇缘 (2013)/…
剧集 剧名 (年)/Season 01/剧名 - S01E01.mkv 绝命毒师 (2008)/Season 04/绝命毒师 - S04E01.mkv
综艺特别篇 剧名 (年)/Season 00/剧名 - S00E01.标题.mkv 现在就出发 (2023)/Season 00/现在就出发 - S00E01.第1期加更….mkv

配套产出：电影写 movie.nfo、剧集写 tvshow.nfo + 每集 SxxExx.nfo，海报从 TMDB 下载。命名模板可配置，字段形如 {cn}.{en}.{year}.{source}.{res}.{codec}，日文作品可以用 {orig} 输出日文原名——TMDB 的 original_language 决定 {orig} 取哪种语言的原名。

工作流：两阶段把关

自动匹配必然有误差，所以流程设计成「机器干活、人只看差异」：

  1. 扫描：ffprobe 读码流参数（分辨率、编码、音轨、HDR），文件名补推片源与发布组。
  2. 联网识别：逐条查 TMDB，表格里回填中英文名、年份、状态（已匹配 / 需人工确认 / 无匹配）。
  3. 预览：生成完整的移动计划（旧路径 → 新路径），不碰任何文件。
  4. 执行：确认后才移动改名、写 nfo、下海报；目标重名的条目自动跳过，不会覆盖已有文件。

识别状态有「筛选」下拉可以快速过滤出未匹配的条目，千行以上的库不用滚动找。执行后自动扫描空壳目录并清理。

匹配引擎：三个关键判断

译名断层时，原名是唯一的钥匙

TMDB 的中文条目用的是官方译名，和资源站的叫法经常对不上。实测案例：文件名 长发公主.Tangled.2010…，TMDB 搜「长发公主」不返回任何条目——它的官方译名是《魔发奇缘》，字面上没有交集。但文件名里的 Tangled 一搜即中。

策略：主查询词的匹配结果不够确定时，从文件名里提取原名段（拉丁连续片段，限 2 个）补搜一轮，两轮候选合并打分。文件名只有中文叫法、没有原名的资源仍然是盲区，这类留给「手动匹配」。

类似的还有后缀污染：碧蓝之海真人版 搜不到条目，TMDB 上对应的是电影《碧蓝之海》(ぐらんぶる, 2020)。「真人版 / 动画版 / 剧场版 / Live Action」这类后缀会剥掉重搜。

年份信号：电影降级，剧集不降级

同名不同片是自动匹配最常见的错误，年份是最有效的校验。电影的年份不符时，匹配结果降级为「需人工确认」，不允许直接执行。

剧集要区别对待：TMDB 剧集条目的年份是首播年，而文件夹/文件名里常写季的播出年。《家有儿女》条目是 2005，S03 实际 2007 年播出——按电影的规则会把 260 个正确匹配全部降级。所以剧集不做年份降级，年份只参与排序打分。

候选窗口用 TMDB 的排序，不要自己重排

TMDB 的搜索结果已经按相关性排好。如果先按标题相似度重排再截断前 N，查询词是英文而条目标题是中文时（相似度为 0），正确答案会被挤出窗口，最后匹配到一部无关片。相似度只用来在候选内挑最优，不用来筛候选。

剧集：集号格式是最大的变量

S01E02、01.flv、[01]、第01话、Dan Da Dan - 01 […]、老九门.EP04.2016…——五花八门。解析器用模式列表依次匹配，全部支持。两个判定规则值得强调：

  • 电影 vs 剧集：同目录下出现 ≥2 个不同集号才判为剧集。防止《101忠狗》这类标题里带数字的电影被误判。
  • 集号解析失败的代价：EP04 这类格式如果解析不出集号，整目录会被判成电影，进而被匹配到完全无关的条目上（文件名带 EP 编号的资源很容易和外语纪录片撞上）。集号解析器的覆盖面直接决定安全性，宁可多加模式，不能漏。

剧集搜索不带年份硬过滤（first_air_date_year 会把正主滤掉），年份只做加权。季号支持中文数字（第二季）。

综艺：播出日期是最强的匹配键

国产综艺在 TMDB 的组织方式和文件名正好能对上：「第1期上」「第1期下」是两个独立集（E01 / E02），每集有 air_date。只要文件名里保留了播出日期（2026-07-25 第5期上.mkv），就能零歧义精确匹配。三级定位策略：

  1. air_date 精确命中（最强，优先）；
  2. 「第N期上/下」在集标题里唯一命中；
  3. 期号数学映射兜底（上 = N×2-1，下 = N×2），验证该集存在。

跨季的期号会撞（S01/S02/S04 都有「第6期上」），所以先用目录里的季号锁定候选季。

非正片归 Specials：加更、花絮、抢先看、先行、无期数的先导篇在 TMDB 没有集条目。这类内容硬编进正片集号会和 TMDB 集序错位，行业惯例是归 Season 00（Specials），按播出日期编 S00E01..n，文件名保留原标题，刮削器显示为特别篇。

安全边界

批量改名是不可逆操作，程序侧做了几层约束：

  • 预览先行：执行前必须看到完整的旧路径 → 新路径计划。
  • 目标重名跳过：多版本并存（8bit/10bit 压制）时不覆盖、不删除，留给人工选择。
  • 空目录清理只删空壳：判定规则是「整棵树里没有任何视频」，含视频的目录永远不动。
  • NAS 上的删除要绕开回收站钩子：Windows 环境下 Python 进程内的 os.rmdir/shutil.rmtree 可能被系统层的回收站重定向劫持，SMB 盘无回收站时直接失败。实现上用 ctypes 调 Win32 RemoveDirectoryW/DeleteFileW 完成清理。

已知限制

  • 外挂字幕不跟随视频移动，需要手动搬到新目录。
  • 片源（BluRay / WEB-DL / REMUX）无法从码流判断，文件名没写时按码率与体积推断，可能不准。
  • ISO 与 BDMV 目录只识别外层文件，不进入 STREAM 逐段处理。
  • 文件名里只有中文叫法、没有原名的资源，译名断层时匹配不上，需手动指定。
  • 同一部片的多个压制版本（8bit/10bit）不是重复文件，程序不自动去重，取哪个版本由人定。

实测数据

库 规模 结果
电影 + 动画电影 333 个视频 命中 329（98.8%），剧集 145 集全中
电视剧 1053 个视频，19 部剧 1052 自动匹配，1 个错别字目录手动指定
综艺 40 个文件 40/40 全自动，含 12 个加更/先导篇归 Specials

回归测试 71 项，覆盖集号解析、译名补搜、剧集/综艺判定、Specials 归档。每次整理真实库前先跑两阶段识别统计，把系统性错配挡在执行之前——识别层的一个解析漏洞（如某种集号格式漏掉）会同时影响整个目录，批量执行前的预览把关是必要的，不是可选的。

结语

本地媒体库整理的核心问题不是改名，而是识别：把发布组的命名语义翻译成 TMDB 条目 ID。译名、年份、集号、期号、播出日期都是线索，可靠性依次递增；线索不足时降级为「需人工确认」，永远比错配安全。

MediaShelf 在 GitHub 开源，Releases 提供单文件 exe（含 SHA256 校验），Windows 10+ 直接运行。欢迎提 issue 和 PR。
