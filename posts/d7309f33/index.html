一、四个仓库，各管什么

打开我的 GitHub 会看到四个仓库，很容易混。先把关系摆清楚：

仓库 可见性 角色 本地路径 我要不要动它
blog-hexo-butterfly-old 私有 Hexo 源码（md + 素材 + 主题配置） E:\test\hexo ✅ 只在这里写
szjmhxd.github.io 公开 展示站（编译产物） E:\test\site-new ❌ 自动生成，不要手改
blog-hexo-Melody-old 公开 旧版博客归档快照 无 只读留存
szjmhxd 公开 个人主页名片（不是博客） 无 与博客无关

为什么第 4 个容易误会

GitHub 有个特殊机制：当仓库名和用户名完全一样时，这个仓库的 README 会显示在你的 GitHub 首页，这叫 Profile README。

所以 szjmhxd/szjmhxd 不是我的博客，是那张像素风的个人名片。它和 szjmhxd.github.io 只差一个后缀，但完全无关。看到 owner/owner 这种形式，先想到个人主页。

为什么源码仓要私有、产物仓要公开

产物仓必须是 public——GitHub Pages 免费版只能从公开仓库发布。

源码仓设成 private，是因为里面除了文章还有工作笔记、内网 IP、服务器路径这类不该公开的东西。虽然产物也是公开的，但至少源头是受控的。

这里踩过一个坑：我一度把源码仓的 source/_posts 完整复制进了产物仓，想着「这样产物仓能独立构建」。结果两个问题：①产物仓缺 _config.yml 和 package.json，压根构建不了；②产物仓是公开的，raw.githubusercontent.com 可以直接读到所有 md 原文——隐私仓形同虚设。后来整段删掉了，产物仓只留编译结果。

front matter 全字段

逐个说：

字段 作用 注意
title 文章标题 会显示在首页、文章页、RSS、SEO
date 写作时间 决定排序和归档目录
updated 更新时间 不填的话 Hexo 用文件 mtime，每次保存都变，建议写死
description 摘要 首页卡片和搜索结果里那句小字，不填会截正文前几十字

top_img 文章页横幅 同上

abbrlink 不要手填

我的 URL 结构是 posts/:abbrlink/，比如这篇就是 posts/d7309f33/。

那个八位十六进制短码由 hexo-abbrlink 插件在首次 generate 时自动写进 front matter。你手填反而容易和别的文章撞。

一旦写进 front matter 就固定了，改标题、改文件名都不影响 URL——这是短链方案的核心价值。

素材目录的对应关系

因为开了 post_asset_folder: true，构建时会自动把素材目录复制到产物里：

asset_img 就是靠这个映射把图正确地指过去。

SVG 图也能直接放

SVG 好处是矢量、体积小、缩放不糊。但注意：SVG 里如果烘焙了文字，改标题后要重新生成——字是画在图里的，不是文本。

图注会变成什么

{% asset_img 图.png 这里写图注 %} 的第二个参数会变成 <img alt="这里写图注">，butterfly 主题（配合 fancybox）会把它显示成图片下方的说明文字。所以图注要写完整的一句话，不要只写「示意图」。

四、封面和横幅怎么生成

每篇文章需要两张自绘图，尺寸是反推 CSS 出来的，不是拍脑袋：

尺寸 用在哪
封面 cover 630×487 首页卡片左侧图框（实际显示 348×269）
横幅 banner 1600×400 文章页顶部（400px 高）

一条命令

跑完，素材目录里会多出 cover.svg 和 banner.svg，正好对应 front matter 里的 cover: / top_img:。

两个图标怎么选（这条最重要）

主图标 = 文章主题的官方 logo。 讲 Docker 就放 Docker 官方图标，讲 Laravel 就放 Laravel，必须是原版矢量，不要自己重画，也不要拿近似的东西凑。

副图标 = 这篇文章对该主题「做了什么」。 必须是个动词：

文章做了什么 副图标
修好了某个毛病 ui-rotate-ccw（反向箭头）
接管了输入 ui-mouse
就地计算 ui-calculator
打通了路径 ui-folder-symlink
分享了内容 ui-share-2
顶部面板改造 ui-panel-top
语音/播报 ui-mic
机器人/对话 ui-bot
天气/推送 ui-cloud-sun
分支/流程 ui-git-branch

判断标准是：副图标要对应本文的动作形状，而不是「这个项目还有哪些图标没用过」。

也不能拿第二个品牌 logo 凑数——一张封面只允许一个视觉主角。

反面例子：早期我所有副图标都固定用「魔法棒」，结果 14 张封面的第二视觉元素长得一模一样，等于没有信息量。后来才改成按动作选。

配色跟着品牌走

现在的规则是背景色由主图标的品牌色推导，不再统一深蓝：

品牌色 → HSL → 色相不动、饱和度夹到 [0.34, 0.72]，再按 --tone 取明度。代码里还写死了三条对比度约束（白字对底色 ≥ 4.6:1），所以荧光色会被自动压暗，不会出现看不清的情况。

有几组常用色：

品牌 色值
Docker #2496ED
Hexo #0E83CD
Ubuntu #E95420
Laravel #FF2D20
GitHub #24292e

什么时候加 --keep-colors

默认行为是剥离图标内层的 fill，让所有部件统一由外层配色决定——这适合 simple-icons 那种单色扁平图标。

但有些图标本身就是配色的，剥掉就丢信息。比如计算器那个图标：「=」长键是金色 #CFB263，其余是深灰 #666666。剥成纯白之后，「这条键是等号」的视觉提示就没了。

这时加 --keep-colors：彩色原样保留，低彩度偏暗的提亮成 #e8eef7（否则深灰在深底上发闷，缩小后几乎看不见）。

验收：--check

它会渲染 banner，取每个绘制元素的真实屏幕框，按 1280/1440/1600/1920/2560 五个视口的 cover 映射求交，逐视口报告重叠面积和出框像素，两个指标都应该是 0。

三个必踩的坑（生成器已内置处理）

坑 1：比例不匹配会被裁。 封面如果用 1200×500（2.4:1），放进 348×269（1.294:1）的卡片会被 object-fit: cover 裁掉左右各 149px。所以封面必须是 630×487。

坑 2：横幅两侧和底部都有禁区。 background-size: cover 在 1280 宽下横向裁 ±160px；而长标题在 1280 下折两行，标题文字上沿会抬到 y=214。自绘内容必须全部躲进 x∈[182,1420] × y<200。

关键认知：最严的不是最宽的屏，也不是最窄的屏，而是「窄屏 + 长标题」这个组合。

坑 3：图标自带 fill 会在深色底上隐形。 很多国内图标站导出的 SVG 内层写着 fill="#000000"，深色封面上一贴就「消失」。生成器会把这类填充剥离，改由外层配色。

五、本地预览

这个脚本用 _config.local.yml 覆盖配置，把 url 改成 http://localhost:4000，然后起服务。

为什么要覆盖域名？因为 _config.yml 里的 url 是线上域名，如果本地预览不覆盖，页面里的完整链接会全指向线上，点一下就跳走了。

一个老坑：PowerShell 里直接 Start-Process "hexo" 会报「不是有效的 Win32 应用程序」。原因是 hexo 是 npm 装的，那个 hexo 是 cmd 垫片不是 exe。必须用 cmd /c 包一层。preview.ps1 里已经处理好了。

预览时重点看三件事：

  1. 首页卡片里封面有没有被裁
  2. 文章页横幅两侧有没有切掉内容
  3. 正文配图有没有 404

最后

这套流程的核心思想是把规则固化进工具，而不是记在脑子里。

尺寸、安全框、配色对比度、图标类型判断、折行判定——这些全部写进了 cover-forge.js。我只需要告诉它「讲什么主题、做了什么动作、什么品牌色」，剩下的它保证不会出错。

同理，deploy.ps1 把「编译→同步→双仓推送→重试」固化，verify_links.py 把「什么该 200、什么该 404」固化。

人负责想内容，工具负责不出错。 这样写博客才可持续。
